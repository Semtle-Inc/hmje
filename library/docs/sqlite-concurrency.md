# SQLite 서버 연결의 경합과 확정 실패

여러 연결이 같은 파일을 사용하는 서버에서는 각 연결을 열 때 다음 설정을
권장합니다. 비동기 연결에서는 `SQLite비동기실행(연결, SQL)을 기다린 결과`를
사용하며, 반환 코드가 `SQLite성공`인지 확인합니다.

```sql
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=5000;
```

WAL은 읽기와 쓰기의 경합을 줄입니다. 동시에 여러 writer가 확정할 수 있게
만드는 설정은 아닙니다. busy timeout은 **연결별** 설정이며, 워커가 SQLite
호출 안에서 잠금을 제한 시간 동안 기다리게 합니다. 모든 연결에 설정합니다.
SQLite가 교착 가능성을 판단하면 timeout 전에 BUSY를 반환할 수도 있고,
LOCKED에는 이 대기가 적용되지 않을 수 있으므로 오류 처리는 계속 필요합니다.

기본 rollback journal과 busy timeout 0에서는 다른 연결의 읽기 거래만으로도
COMMIT이 `SQLITE_BUSY`(5)로 실패할 수 있습니다. 이 경우 쓰기 거래는 아직 열려
있고, INSERT의 성공은 파일에 확정됐다는 뜻이 아닙니다. `SQLITE_LOCKED`(6)와
확장 코드도 주 오류 코드로 분류합니다. `DB거래확정`은 실패 상태와 원래 오류
코드를 반환하며, BUSY/LOCKED는 확정 여부 불명으로 표시하지 않습니다.

`데이터베이스 거래 안에서` 블록은 시작·실행·COMMIT 실패를 기존 실패 처리
경로로 전달합니다. `DB거래상태.오류코드`는 SQLite 코드(5/6)를 보존하고,
비동기 `실패하면`의 `실패코드`는 기존 런타임 규약에 따라 -5/-6입니다. 확정되지 않은 거래는 `끝으로` 경로에서 롤백합니다. 서버는
블록이 성공적으로 끝난 뒤에만 201 같은 성공 응답을 반환해야 합니다. 직접
`DB거래확정`을 호출하는 코드는 반환 상태를 검사하고 실패 시
`DB거래되돌리기`를 호출해야 합니다. 원시 `SQLite커밋` API는 SQLite와 같은
계약으로 열린 거래를 유지하므로 직접 재시도 또는 롤백할 수 있습니다.

비동기 DB worker는 연결별 작업을 직렬로 처리하고, 거래 소유자가 롤백을
끝내기 전까지 다른 작업의 진입을 막습니다. SQL 실행과 준비/step의
BUSY/LOCKED는 결과의 오류 코드로 전달합니다. worker가 임의로 문장이나 거래를
재실행하지 않습니다. 자동 재실행은 부분 실행이나 외부 부수 효과를 중복시킬
수 있습니다. 재시도가 필요하면 전체 거래의 멱등성을 확인하고 횟수/시간을
제한합니다. 백업 API의 제한된 잠금 재시도는 별도의 계약입니다.
